## 2. OUTCOME — in the owner's language

The owner will see, in the record, one row for the birth of every program the system runs: the system loaded this program, from this image, with this sealed set of rules, and the program cannot ask for more than that set while it lives. He will see that no program can create or change a view — views are the system's alone, computed from rows on read, as they are today, now written as a rule. And he will see every actor placed, on demand and from rows, on a matrix of dimensions he named — structured or unstructured; one actor or an organisation of actors; one live session or many; inside the computer or outside it; ordinary program or one that touches hardware — without one new field on the actor row.

He will see that every program the system runs lives in the glass box he drew for the AI organisation: two watched openings, one to its user and one to the system, both declared on the program's birth row, no third opening, and no program ever moving anything to another program except through its own system-facing opening with the crossing on the record. That box is not a special enclosure for AI; it is what a program is in gov-os (design/39), and this campaign is where the box is written down as rows at the moment of birth. Past this campaign's own rows lies the horizon this estate has carried since campaign 2: the living organisation, TWC's thirty-three seats re-hosted as the reference tenant, every seat a program in its box, the watched braking the watchers as daily practice (§11).

## 3. TARGET BEHAVIORS — numbered, testable

- **B0 A KIND IS A PLACE, AND RULES BIND REGIONS.** Every split of the ontology chain and every CGL grammar is an axis with a closed founded vocabulary; an item established by an act sits at one place on every axis, read from its establishing row and its capability rows, never stored as a kind; a rule binds a region of that space, never a name; an item inherits every rule whose region contains its place. "Create driver" is CREATE-ACTOR at the driver's place plus its capability row, and every item, actor, program, hardware-touching and capability rule arrives by containment. Check: a driver established without the word "driver" on any row is bound by every rule the driver region carries; a planted rule naming a kind by word instead of by region is refused at the door; a new kind founded as a new operation is refused. (the owner, 2026-09-16: "if we say create driver, it should inherit the whole matrix tree of program, structured data actor, actor, item"; design/59 Part 1b)

    B1. THE LOAD ACT. When the system starts a program as a process, one row is written before the program's first act: actor SYSTEM, operation LOAD-PROGRAM, object the program entity (design/39: an entity with an append-once identity), fields: the image digest, the sealed rule-set digest (B2), the process view's handle. A process without a load row is refused at its first act by name. Test: start a program, read the load row; plant a missing row → the first act refused. THE LOAD ACT IS ONE FUNCTION FOR EVERY ACTOR (owner, 2026-09-17: "user A login, load rule related to user a as actor, object and target, when log out, clear, then user b login, same process ... is this same for all other actors?"): a program's process, a human's session and an AI's session are each an incarnation born by the same act -- one row, the actor's sealed rule set computed from the master views (every rule whose region contains the actor as actor, object or target, B0/L7) and carried on the row -- and ended by one row; nothing is 'cleared', because the sealed set is a derived thing dropped at the end and the views are computed on read. The class and the identity differ per incarnation; the act does not. THE SET IN MEMORY IS NOT WHAT DECIDES (owner, 2026-09-17: "the list of rules will be created on ram and somehow made tampering proof? (possible for ram?)"): memory cannot be made tamper-proof by software and the design does not try; the set is made tamper-EVIDENT (its digest is on the load row, and a set that no longer matches its digest is refused as stale, P4) and the decision is made tamper-IRRELEVANT (I3: the gate decides every act against the live record, never against the sealed copy; the copy is a derived convenience). A changed copy in memory changes nothing the record decides. INSTALLATION IS A SEAL PLUS A DECLARATION, NEVER A SCAN (owner, 2026-09-17: "how gov-os workout what [an AI assistant program].exe is (the whole program with folder) at point of installation? or scanning config files or what?"): the whole program -- folder, executable, its files -- is sealed as ONE image and its digest is the program's identity (the SealedArtifact idiom the body already runs on the interpreter image: refuse a load whose bytes do not match the seal); the installer's act declares the program's parts as rows -- its actors and their classes (one, or an organisation, B5), and for each the operations it will invoke, hence its cells; gov-os reads no config and infers nothing from the files: what the declaration does not name the program cannot do (the bank has no counter), and an act outside the declaration is refused and recorded, which is how a wrong declaration is discovered. The load act (B1) then checks the seal against the digest on every start and computes the sealed rule set (B2) from the declared class and identity. DATA AGAINST INSTRUCTIONS (2026-09-18, the owner's push on runtimes): the one test of any content a program opens -- CAN THE FILE MAKE THE PROGRAM ASK THE SYSTEM FOR SOMETHING NEW? No: data, an ordinary program, its ask-set fixed by its own sealed code. Yes: instructions, and the program is a RUNTIME for that content, whose declared touch points must bound every ask its content authors; the property is per content, not per program (a document is data until its macro runs, and at that moment its host is a runtime for the macro). An OPAQUE THING at the border (firmware, a device, a stick) registers automatically at first contact as an ITEM, never an actor: what was measured from outside is fact, what it claims of itself is recorded as a CLAIM with its source; the item/actor line is read from its crossings, never stored -- an item only answers inside its declared shape, an actor ORIGINATES a signed ask (fingerprint is what we measure; signature is what a secret-holder produces), and the day a passive thing first originates, the refused ask is itself a row.
    B2. THE SEALED RULE SET. At load the system computes, from the master views (design/25 v2), the set of rules that bind this program (derived by actor class + the program's identity + its bound devices), seals it (a digest over the canonical set), and carries the digest on the load row. The program may ask only what the sealed set admits. THE GATE STILL DECIDES EVERY ACT AGAINST THE RECORD AS IT STANDS: a rule overturned after the load counts at once (the outside reader's "stale permission" finding, DIGEST-C5, is the shape this must never reintroduce). The seal is the program's contract and the witness of its birth, never a cache the gate trusts. Test: load, overturn one rule, the next act is refused with the live rule cited and the seal named as stale; plant a gate that reads the seal instead of the record → red.
    B3. VIEWS ARE THE SYSTEM'S. A founding rule: CREATE-VIEW and every view-writing operation is admitted to actor SYSTEM only; every other class reads. Test: a human, an ai and a program each attempt a view write → refused by name; SYSTEM's founding seeds unchanged.
    B4. STRUCTURED IS A PROPERTY OF THE OPERATION ON ITS OBJECT. A rule of record: an operation is structured when its effect is fully fixed by its declared parameters without interpreting content (moving a whole cell; "remove the final full stop only"); unstructured when the effect depends on interpreting content. Natural-language processing is unstructured work by this test; under the cell law (design/52 L28) a program performing it acts in the ai class, not the program class. Test: the operation catalogue carries the arm per operation; a planted operation that interprets content but declares structured → refused at founding. HOW AN INSTALLED AI IS TOLD APART (owner, 2026-09-17: "if I install [an AI assistant program], there are bunch of s stuff in the interface but also some u stuff where AI process the info, how do we identify it?"): never by an asserted claim about the actor and never by guessing what it can run -- by the operation it invokes, whose founded definition carries its cell (the op_definition row already has a 'cell' field: BIND-DEVICE is S). The interface acts are S operations; the acts where the AI interprets content are U operations it must invoke as such; a program invoking a U operation acts as ai-class for that act (L4's class consequence) and meets the ceilings of that class; an operation not declared does not exist (the bank has no counter). P1's census arms all 94 operations with their cell; a U act attempted through an S operation is the gap the cell law (design/52 L28) closes from the AI side and P1 closes from the operation side.
    B5. THE MATRIX, COMPUTED. Five dimensions, each a derivation from rows and each a derive dimension of the view tree (design/25 v2 DERIVE_DIMENSIONS grows by four): (1) structured/unstructured — from the actor class; (2) single/organisation — from the containment rows (an organisation is an actor that contains actors); (3) one live session/many — a rule row on the actor limiting live incarnations (a process is a view of the actor, design/39); (4) inside/outside the computer — by how the actor's acts arrive: the kernel's crossing or the one connection (design/52 Q9, the "external" question, answered as a dimension, not a class); (5) ordinary/hardware-touching — by the device operations the program is bound to (REGISTER-CAPABILITY / BIND-DEVICE rows; drivers are programs bound to devices, not a class). Test: each dimension's view recomputes from rows; the actor row gains no field (a byte-diff of the CREATE-ACTOR shape). AN INSTALLED PROGRAM AS AN ORGANISATION (owner, 2026-09-17: "would gov-os get to a level of seeing the individual sub processes into the unbreakable atomic level so the program organisation is made of mini-process workflow of different s and u?"): gov-os never sees inside a box (design/39 §5: watching is not copying; record decisions, sample flow), so it does not auto-tag a program's internals -- the atomic level it sees is the ACT at the gate, each an invocation of a declared operation with its cell. One executable is one actor of one class today, and an ai-class actor is refused at every S operation (L28), so a [an AI assistant program].exe whose interface does S work and whose model does U work is DECLARED as an organisation, dimension 2: a program-class actor for the interface and an ai-class actor for the model, each in its own box, related by containment rows, the gate seeing which one invokes. What a program does not declare as an actor it cannot do as one (the bank has no counter); deeper than its declared actors and their acts is invisible by design, and that is the guarantee, not a gap.
    B6. THE ACTOR CLASSES STAY THREE. human, ai, program; system the one border entity. No fourth class is minted by this campaign; what would have been "external" is dimension (4).
    B7. THE TWO CHANNELS, DECLARED AT BIRTH. The load row (B1) carries the program's two openings — its user-facing channel and its system-facing channel (design/39 §3) — as fields; any further opening a program declares or attempts is refused by name; a move from program A to program B is A's own act through its system-facing channel, witnessed and recorded, and B's receipt through its own. The one declared fast path (the shared-memory grant, design/39 §5 cap 1) is recorded at the border and stays honestly unaudited inside. Test: a program's third opening → refused; A→B direct → refused; A→system→B → two rows, one crossing. This is the TWC glass box as the general definition of a program, not a special case. WIDENED 2026-09-18 (dialogue 10, the owner's words): the person-facing channel is NEVER OPTIONAL -- every actor's box carries it by construction, two-way; a declaration shapes what rides it, never removes it; what a given person may do on it is graded per user per service (see-and-inspect only, or see-and-change) by the permission intersection. ## 3a. THE ACTOR'S VIEW AT LOAD — the part, written on the owner's word (2026-09-17, "go with writing the part for loading actor view")

**What it is.** Every actor that comes into contact with the system — a program started as a process, a human at login, an AI at the start of a session, a driver bound to a device — is an INCARNATION, and an incarnation begins with one act and ends with one act. The beginning act (B1) writes one row: actor SYSTEM, operation LOAD (the one name for all classes; the class and the identity are fields), object the actor's identity row, with three fields — the identity's seal (for a program, the digest of its sealed image, checked before the row is written; for a human, the verified identity the signing law transfers from live to stored; for an AI, its declared model identity), the DIGEST of the actor's view (below), and the incarnation's handle. The ending act writes one row the same way. Nothing between them is stored as truth.

**What the view holds.** The actor's view is computed at load from the master views (design/25 VERSION 2) and it holds exactly what deciding an act by this actor needs: (a) every rule whose region contains the actor's place — as actor, as object, or as target (B0/L7: a kind is a region; the actor's place on every axis is read from its rows); (b) every operation the actor may invoke, each with its founded definition — its parameters, its cell (S or U), and its CHECKS, because "if the checks pass append the decision citing the law, if not refuse citing the terminal rule" is the operation's own row and travels with it (the braking computer, B16); (c) the items the actor is related to by containment, custody or bind rows (its organisation, its devices, its worlds); (d) the ceilings of its class, composed by intersection as views.py already composes them (:1647-1701). Not in it: any secret, any other actor's view, any row outside its regions.

**Touch points instead of inherited authority (the owner, 2026-09-17: "how to work out the required touch points and permission instead of the old ways of inheriting user etc").** The desktop way gives a program the whole authority of the user who starts it; a capability system gives it only the capabilities it holds. This design takes the second road and names the capabilities as ROWS: a program's permission is the INTERSECTION of three things — the TOUCH POINTS it declared at installation (the operations it will invoke and the regions it will invoke them on, B1's declaration), the grants the invoking actor actually holds (the rows of the record, never the user's whole standing), and the rules of the region the object sits in. A program started by an administrator therefore holds no more than it declared, and an administrator's grant it did not declare it cannot use. The view at load is that intersection made explicit, and the gate re-derives it at every act (I3); the declared touch points are the new field this campaign founds on the actor row's declaration, the intersection is machinery the ceilings already have.

**How the touch points are worked out (the owner, 2026-09-17, pressed: "how to work out the required touch points ... instead of the old ways of inheriting user"): by MEASUREMENT, the way this estate worked out its own kernel's touch points. A program is run in its box with every crossing a row — the two openings see everything it asks of the system — and the set of operations it invoked, on which regions, IS its touch points; that measured set, and nothing guessed, becomes the declaration sealed with the program at installation (the 5s2 census over 193 modules is the precedent: the twelve kinds of work were read from traces, never from anyone's word). The maker may declare narrower than measured, never wider than the region's rules allow. At run, an act outside the declaration is refused and RECORDED, so a touch point the measurement missed shows itself as a refusal row, and admitting it is an act by someone holding the grant — a widening is always a row, never a silent inheritance. The user's standing enters only as the second term of the intersection: what the invoking actor holds; the program gets none of it beyond its own declared set. So the permission is derived from what the program was seen to touch, bounded by what the actor holds and what the region allows, and it is re-derivable by running the program again.**

**Before the first run (the owner, 2026-09-17, angry: "how do we know the permission of a program before the first run? ... getting a list of rules re the program before anything"): from the sealed image itself, without running it. A program can only ever invoke operations that exist by name in the registry (an unregistered operation does not exist), so a READ of the sealed image — the operation names its code references, the regions and object kinds it names — gives the list of what it COULD touch, derivable from the bytes alone and repeatable because the seal fixes the bytes; the maker's shipped declaration is checked against that read, and a declaration wider than the code is cut to the code, a declaration narrower is kept. The list of rules for the program before anything is then computed: every rule whose region contains the program's class, the region it is installed into, and each of those operation names — the same derivation as the view at load, done at installation over the static list. The run-time measurement above REFINES that list (a static read over-counts what is never reached and can miss a name built at run time), and the refusal row at run is the net under both. Three sources before the first run, all static: the region's rules for its class, the read of the sealed image, the maker's declaration cut to that read.**

**Sub-processes (the owner, 2026-09-17: "opening [a game store program] ... a million other small processes even the screen is showing one window ... [an AI assistant program] ... sessions running as process actor with identity, with sub-process of the s operation of the process vs the u operation of the llm behind it"): every process start is one of the twelve kinds of work the kernel performs, so each sub-process a program starts is seen at the gate and born by its own LOAD row — its own sealed image (or its parent's, if it is the same binary), its own touch points read at installation from that image, its parent named by a containment row. A program that fans out into many processes is therefore an ORGANISATION of process actors (B5, dimension 2) COMPUTED from the load rows, not declared by anyone; the one window on the screen is one of them. For an installed AI: if the interface and the model are separate processes, each is an actor with its own row and class — the interface program-class with S operations, the model ai-class with U operations — and the gate sees which one invokes; a chat session is an incarnation row under the process, the way a login is. If the model runs inside the interface's own process, the gate cannot see inside that box (design/39 §5) and the split holds only by the installation declaration, which is why an AI product that wants its S half to act as a program must ship it as its own process. The hierarchy is one shape at every level: program (a sealed image) > processes (load rows, containment) > sessions (incarnation rows).**

**Where it lives and how it is trusted.** In memory for the incarnation's life, as a derived thing; on disk if written, as a derived copy — the same standing as the disk-stored derived views the boot self-check verifies ("the disk-stored derived views are correct", the owner's own wording, design/47 §9). Its digest is on the load row; a copy that does not match its digest is refused as stale (P4's refusal); and no decision is ever taken against the copy — the gate decides every act against the live record (I3), so a tampered copy in memory or on disk changes nothing the record decides. Memory is not made tamper-proof; the view is made tamper-evident and the decision tamper-irrelevant.

**When it changes.** A rule minted or retired while the incarnation lives does not edit the view; the next act sees the record, and a view whose digest no longer matches the rules in force is stale and recomputed at the next load. A view is never patched in place: it is derived, dropped, derived again.

**For each class, the same act.** Program: seal checked, touch points read from the declaration, view computed. Human: identity verified by the signing law, view computed from the rules that name the person as actor, object or target and the items in their custody. AI: model identity declared, class ai, U operations only (L28), view computed the same way; an AI inside an organisation (B5 dimension 2) has its own view, its interface program its own. Device driver: bound by a BIND-DEVICE row, its view the declared I/O window and the device's rules. One act, one row kind, one derivation; the classes differ in what the identity is and which cells the ceilings allow.

**Tests (the rows, P3 and P4).** A load row precedes an actor's first act or the act is refused; the digest on the load row equals the digest of the view recomputed from the record at that instant; a view copy with one byte changed is refused as stale; an act outside the declared touch points is refused by name though the invoking user holds the grant; an act inside the touch points but outside the user's grants is refused by name though the program declared it; the end row closes the incarnation and a later act on its handle is refused; the derivation run twice over the same record is byte-identical (universal derivability).

**The definitive check (the owner, 2026-09-17: "defintiive architecture modular etc check?").** Against the three criteria and the minimality gate: the whole of this section founds TWO row kinds (LOAD, END) and ONE field (the declared touch points on the program's declaration); everything else — the rule list at installation, the view at load, the organisation of processes, the permission as an intersection — is DERIVED from rows already founded (the sealed image and its seal, the operation definitions with their cells and checks, containment, grants, regions) and re-derivable by running the derivation again. Nothing is stored that can be computed; no new operation kind is minted for a new kind of program (L7: a kind is a place). Modular by row kind: the seal, the declaration, the load row and the region derivation are each their own rows and each replaceable without the others moving. Against the existing definitive: design/39 (a program is an entity, a process is a view) holds — the load row IS the process view's birth; design/25 (views computed on read) holds — the view at load is a derived view with a digest; design/52 L17/L28 (three classes, the cell law) hold unchanged. Nothing in it contradicts a founded row; it is an extension by rows, which is the only kind this constitution admits.

**Caps.** The declaration's shape (which rows carry the touch points) is P3's to found and the owner's to word at its gate; the disk copy is optional and its format is the view tree's (design/25 VERSION 3 at P5); the human login's identity step is the signing law's (design/37), not this section's.
