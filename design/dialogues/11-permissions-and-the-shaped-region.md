# Dialogue 11 — permissions: the folder, the dependency, the shaped region (2026-09-18)

The owner's words verbatim (his spelling kept); the architect's answers as filed the same night.

D11.1 OWNER: "a top folder with sub-folder a b c d e, we give user access to top folder and later exclude jsut sub-folder a, how normal os do this and how gv-os does this?" ARCHI: the desktop stores permission on each thing as frozen copies (recursive re-stamping, deny-beats-allow piles, the unanswerable audit); gov-os: a grant is one rule on the top region (a region contains what is inside), the exclusion one later rule, every act decided fresh — and the audit is a reading.

D11.2 OWNER: "so how to know conflicts of which take priority with two rows?" ARCHI: mostly no conflict exists — permission composes by intersection, the narrower rule wins by construction; a genuine same-frame must/must-not contradiction is never smoothed: the act is undecidable, refused citing both rows, the contradiction a standing finding.

D11.3 OWNER: "or I should ask, is this two different permission of different object or actually a single permission but change in obj shape?" ARCHI: both exist as different lawful acts — amend (retire + re-grant narrower: one permission reshaped) or overlay (a new refusal): same computed reach, different recorded meaning.

D11.4 OWNER: "is file A read and file A write two permission or one permission as write covers read?" ARCHI: two, always; write never covers read — permission attaches to the operation; write-without-read is legitimate (the letterbox); no operation implies another (a hidden implication is an unwritten rule).

D11.5 OWNER: "we basically can have permission with dependency, write needs read exist before it can be granted... this may not to be core/constitutional rule?" ARCHI: yes and yes — a dependency is a rule whose object is the GRANTING act, checked when the grant is decided (governance = activity with a rule as object); and deliberately ordinary, not constitutional, so the letterbox stays lawful where wanted.

D11.6 OWNER: "reshaping we were talking about — two stacked permissions or reshaping of permission?" ARCHI (first position): stack by default (needs no power over the original rule; two decisions kept), reshape as the correction form. Status then: stacking built today; reshaping waits on the retiring act (campaign 8).

D11.7 OWNER, the correction that became canon: "i feel like stacking of permission is more dirty and chaotic vs reshaping like it is not change of permission level, it is change of the object that is being applied into so the 1 + 2 -4 etc is more a add remove on objective shape. that means a applied object is always defined against the permission you get me?" ARCHI, revised with reasons: adopted (design/56 v0.31). Stacking's cost is reach-as-computation-over-N-rows — the desktop disease reborn one layer up. The canon: ONE permission whose REGION is a defined object edited by ACTS (add a piece, remove a piece, each a row) — the reach always one readable shape, the history the fold of the edit rows, "the applied object is always defined against the permission". Separated powers kept (who may reshape a region is itself ruled, per region); the security overlay kept as the PROTECTION layer — always-refuse, separate authority, never lowered — a different KIND, not a stacked grant; the pile's chaos came from mixing the two kinds. Stacking survives only as interim mechanics until the retiring act lands.

D11.8 OWNER: "is this a common permission / security design? have people thought about this before?" ARCHI (trained knowledge, uncited): the pieces have ancestors — mandatory-versus-discretionary control for the two-kinds split; capability systems for object precision; policy-kept-in-version-control as an out-of-band shadow of the history — but the mainstream built stacking with precedence (first-match tables, deny-beats-allow policies) and its unauditability at scale is famous. The combination here is available because the substrate is record-first: they store policy as documents, gov-os stores it as acts, so edit-history is native and the one-readable-shape form is free.

Caps: the answers are the filings of the night (design/56 v0.31 the canon; the dependency and two-permission answers dialogue-level, inherited by the trees at P0); nothing here is built beyond what campaign 8's stages name; the prior-art answer is trained knowledge, uncited by sources.

D11.9 OWNER (2026-09-18, completing the canon): "so there is reshaping and there is right level stacking only when there is add of 'action' of aaot right e.g. read + write? so rule atomisation should just be considered as a a o t specific all the time, and if a is modified or o is modified etc, it should be reflected as modified rather than stack or what etc right?" ARCHI: exactly right, adopted (design/56 v0.32). A permission atom is actor-action-object-target with ONE action — the action is the atom's identity; the other three coordinates are its shaped regions. A change to any shape (actor widened, object carved, target narrowed) is a MODIFICATION of the one rule — edit rows on its shapes, never a second rule. The ONLY lawful stacking is a new action: a new atom beside (read and write are two atoms — the two-permissions law lands here as a consequence). His cut makes the grant fabric fully readable: one atom per action per slot, each atom's shapes carrying their own edit history, protections a separate kind above.
