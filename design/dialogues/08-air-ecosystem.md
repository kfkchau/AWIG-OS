## D08.1 — the ask (owner)
"ecosystem thinking for gov-os penetration like air." Archi's derivation:
air spreads because it asks nothing; the smallest piece any actor can
take without taking us is THE ROW (actor, action, object, target, rule

## D08.2 — internal modularity, honestly (owner asked)

rebuildable from rows), NOT yet by packaging (one codebase, no published

except two fixed things — the row grammar, and the law that every act

rendering, parallel tools). Guard per join: the conformance test that

## D08.9 — replacing an old-code function, and giving it back (owner asked, 2026-09-05)

The install pack for one function = four pieces: (1) INTAKE — the old
function's data read into rows while the old code keeps running (AD);
(2) EXPORT VIEW — rows rendered back into the old code's own format
(the old shape is a VIEW over the record, recomputed on demand, never
lost); (3) THE ROUND-TRIP TEST — old -> rows -> old byte-identical AND
the old code gives the same answers on it (the estate's own
export->wipe->import->byte-identical gate, design/13); RULE: no
byte-identical round trip, no takeover; (4) THE SWITCH — the old
callers' interface stays; gov-os answers behind it (performer-swap per
function). REMOVAL = the same walk backwards as a handover (design/46
ceremony): export in the old shape, byte-verify, old code proven
identical on it (the takeover test reversed), receipt, line-verified
removal, departure row. The test that lets us in is the test that lets
us out.

## D08.43 — how industry keeps a unique signature from clashing (owner, 2026-09-08). TRAINED KNOWLEDGE, Estimate — High, dated; no source read this turn.

Four mechanisms, used together; the last two are the ones that matter in practice.
1. **Enough random bits.** A 256-bit key, a 128-bit random id (UUID v4), a 256-bit hash: the odds of two colliding follow the birthday bound — you need about 2^(bits/2) draws before even odds, i.e. ~10^19 ids at 128 bits. Nobody guards against that number; it is treated as zero.
2. **A good source of randomness — this is where real failures came from.** The OS's cryptographic random source (getrandom / /dev/urandom, seeded from hardware). Every famous "duplicate key" incident was a BAD SOURCE, not bad math: Debian's 2008 OpenSSL bug (keys drawn from ~32k possibilities), embedded routers shipping the same key, virtual machines cloned from one snapshot drawing the same "random" numbers. The clone case is gov-os's FORK case (D08.42).
3. **Structure where uniqueness must be guaranteed rather than probable.** A registry hands out a prefix and each holder counts inside it: MAC addresses (IEEE block + vendor counter), DNS names, time-plus-machine ids (UUID v1, Snowflake/ULID = machine id + timestamp + sequence). Guaranteed, but it needs an issuer above the system — the PKI/registry shape C4 refused for identity.
4. **Self-certifying names + detection.** The public key IS the name (SSH host keys, Tor onion addresses, IPFS peer ids, blockchain addresses): no issuer, uniqueness by (1)+(2); and a transparency log or chain so that if two parties ever present one key, the divergence is SEEN (certificate-transparency logs; our chain).
5. **Hardware-bound keys against copying.** A key made inside a TPM / secure element cannot be exported, so a clone cannot carry it — this is the only mechanism that turns "a fork is detectable" into "a fork cannot be made", and it is C7's firmware/hardware anchor (design/37 orbit), not C5's.

**gov-os today, by that list:** (1)+(2) via the boot ceremony's random seed from the OS source; (4) the bound public key + genesis hash as the name and the chain as the detector; (3) refused by design; (5) named for C7. Honest cap: "never in any possible way" is not a property anyone has; "never by chance, and never unseen" is the property, and (2) is the one to test — a planted bad-randomness world (a fixed seed) must be REFUSED by the ceremony, which is an EP-47B acceptance to add by name.

## D08.46 — a secret the system itself cannot read, yet still works (owner, 2026-09-08: "how do we make the genesis or the system operation generate a secret that even itself cannot read? but the secret can still work?"). Trained knowledge, Estimate — High; mapped to what is built and what is not.

Five ways, weakest to strongest; gov-os has the first and the fourth, C7 owns the second and fifth, the third is a check kind.
1. **No read path, by construction (software).** The secret is stored as its HASH (the vault: `seal` writes the hash, `compare` answers yes/no, nothing returns the value — EP-19) or held behind a surface whose only method is a USE (the signer: `sign`, never `get` — EP-47). The secret "works" because the system performs the operation with it or checks a candidate against it; it "cannot read" because there is no method that returns it, and the estate's guards pin that surface. HONEST CAP: the bytes are in process memory; root, a debugger or a core dump can read them. Software gives "no LAWFUL read path", not "no read at all". This is the running estate.
2. **Born inside hardware, never leaves.** A TPM / secure element / HSM / enclave GENERATES the key inside the chip; the CPU can only ask "sign this" / "unwrap that"; the private half never exists in RAM; even root cannot read it, and the chip can ATTEST that the key was born inside it. This is what "even itself cannot read" literally means, and it is C7's hardware anchor (design/37 orbit, the firmware anchor, VM-3), not C5's.
3. **Split so that no one holds it.** Secret sharing (Shamir) and threshold signatures: the key exists only as k-of-n shares; signing is a ceremony of enough hands (threshold schemes sign WITHOUT ever reassembling the key). "Even itself cannot read it, but it works when enough of us are present" — the governance-shaped answer, diversity with a guaranteed say applied to the system's own key. In gov-os it is a QUORUM check kind over a key ceremony (design/42 §2.5) — the owner's one word when a row needs it (design/51 §11 item 3); the two-witness diving buddy (EP-45) is its two-body cousin.
4. **Derive at use, store nothing.** The key is computed from something presented at the moment of use (the id-card secret → HKDF → sign/open keys, EP-46/47's account keys): between uses it does not exist anywhere, so there is nothing to read. Already the design for ACCOUNT keys.
5. **Sealed to the system's own measured state.** TPM sealing: the secret unwraps only when the measured boot matches — the system can use it only while it IS the attested system; a modified system gets nothing. This is the natural join of the engine's self-attestation (EP-40) with hardware: C7.

**The rule under all five:** a secret "works without being readable" whenever the only operations on it are USE (sign / unwrap / compare) and the place that holds it has no return path — software makes that a discipline, hardware makes it physics, splitting makes it a ceremony. Nothing minted here; C7's intake gains items 2 and 5 by name.

## D08.48 — max unfakeable AND max private: reveal only what the rule needs (owner, 2026-09-08: "max flex — a hash that reveals certain signature parts and protects others; a handshake so we know this is an actor from gov-os version x, human / process / AI, but hide all other actor info. what function, and why?")

**The function: SELECTIVE DISCLOSURE** (trained knowledge, Estimate — High): prove chosen facts about a signed identity without revealing the rest, with the proof still bound to the signature so hiding weakens nothing.

**The mechanism that needs no new cryptography — a signed tree of facts.** The identity is not one blob but a TREE: each fact a leaf (body key; founding version; actor class = human / process / AI, design/43's three classes; the tunnel's permitted class; the head@seq; the establishment row's id; …), each leaf salted and hashed, the ROOT signed once by the actor's key (and the code block by the project key). At a crossing the sender presents: the root signature, ONLY the leaves the receiver's rule requires, and each leaf's hash path to the root. The receiver verifies the root and the paths and learns exactly those leaves — nothing else, and nothing else is even guessable (the salts). This is the hash-chain discipline the record already runs, turned sideways (SD-JWT does exactly this in the identity industry).

**Why it is needed — four reasons, in his order of weight:**
1. **Least disclosure at the border.** A crossing should carry what the receiver's RULE needs to DECIDE and nothing more. The tunnel already binds "permitted class" (EP-49B); the rule says "to submit this kind of draft, reveal: actor class, founding version" — so disclosure is RULE-DRIVEN, recorded, and a withheld required leaf is a recorded refusal. Governance decides on class and authority, not on who exactly.
2. **Privacy of actors across bodies.** An actor's full identity and history must not become linkable across every peer it ever spoke to; what a peer holds afterwards is a root hash and the leaves it was owed — enough to attribute the crossing later (the actor's own record resolves the root), not enough to profile.
3. **Unfakeability kept.** Every revealed leaf is bound to the signed root; a forged leaf fails its path; a stolen leaf without the root proves nothing. Hiding costs no proof.
4. **Secrecy of the rest.** The unrevealed leaves are never derivable — salted hashes — so "protect other parts" is a property, not a promise.

**Where it lands in C5:** EP-49B's proof method presents leaves + paths (the four-tuple's "permitted class" is a REVEALED leaf); EP-49D's receipt cites the root hash and the revealed-leaf set (so both sides can later show exactly what was disclosed); a DISCLOSURE-BY-LAW row: the receiving body's rule names the leaves a crossing of each class must reveal (data, decided by the existing gate — no new check kind). design/51 N4 gains one sentence. **Later, named not minted:** UNLINKABLE per-peer keys derived from the body key (so two peers cannot even join the roots) and ZERO-KNOWLEDGE predicates ("version ≥ 1.40", "a human", without the value) — C6's paper, when two bodies with their own records need it; both use the same tree.

## D08.49 — actors in three classes, and the two cuts that bound them (owner, 2026-09-09: "we have human, ai, and system-type (software/program)… human can do both, ai can only do u, system type can do s… system-type there are program/software terminally talking to hardware… software that only talk to other software… software that may talk to ai or human… org, we can have ai org, human org, or org that have both")

**The classes, his words kept.** Three actor classes: **human**, **AI**, **program** (his "system-type"; the filed word is program — a program is an entity, design/39 §2; its processes are its incarnation). **"System" stays the one border entity** (design/43 §5) and is not a class of programs. The constitution today uses two class tokens ("system", "human") and declares NO domain for the field — a gap older than C5, closed by the vocabulary rule below.

**The first cut — processing, structured vs unstructured — is DERIVED, not chosen.** Human: both. AI: unstructured only. Program: structured only. The reason is replay: a structured rule's value is that the record replays it to the same answer; a program's output is a function of its inputs, so it may be the ARM of a structured rule and replay holds; an AI's output is not, so an AI as the arm of a structured rule breaks replay; a human may do both because a human's judgment is what an unstructured rule asks for, and a human following a structured rule is replayable by the rule's own text. **The cut bounds who EXECUTES a rule, never who may ASK:** an AI may submit an act that a structured rule decides; it may not be the thing deciding. This is the s-rule / u-rule gradient (design/43 §6) landing on the actor.

**The second cut — reach — is the program sub-classes, and it is half in the record already.** Hardware-touching programs are the device side (a device class exists at registration). Software-to-software is the socket and channel side. Software-to-AI-or-human is the channel and tunnel side, where the tunnel already binds a permitted class of counterpart. So "talking-to permission" groups on the TARGET slot of the act: a reach class names which classes of counterpart an actor may open a path to. A program that touches a battery and also talks to an AI needs both reach classes explicitly.

**Orgs are not declared a class; their class is COMPUTED.** Occupants are recorded, so human-only / AI-only / mixed is a fold over the live occupancy instances at the tips. Ceilings apply at the actor when it acts, so a mixed org may hold a grant its AI occupants cannot use. What the computed org class is FOR is the rule about say: an act at rule level by a mixed org may be required to carry a human occupant's countersign — diversity of perspective with a guaranteed say, as one rule reading one view.

**Open for the owner's word when the paper puts them:** whether an AI may ever hold a device reach class; whether "external" (a peer body) is a fourth actor class or a reach class of the border.

## D08.50 — categories are acts, ceilings only shrink, and the three frames (owner, 2026-09-09: "do you think we need some grouping and categorisation to auto restrict power?… how would categorisation look in your mind… show me the grouping structure, we will be using venn2 right?… what is max possible for that actor group")

**Restriction is already the default; a category adds a bound, never a power.** Power is the grant; no grant, the act is refused. What a category adds is a CEILING over what any grant may say. The asymmetry is the whole design: a class can only shrink what a grant may say, never widen it; the grant stays the one place power lives, readable and revocable one by one. This keeps the industry's role-based template out (there the role IS the power and membership is the act of granting).

**Four things, all records, nothing stored as a status.** (1) The vocabulary is a rule in the constitution: the actor classes and the information classes, declared; a class not in the list cannot be written; adding one is a versioned amendment (the declared-set condition of 2026-08-20 applied to classes). (2) A category is an ACT with evidence: classify / unclassify — actor = who classified, object = the entity or the information, target = the class, with the evidence and the rule cited; the class of anything at a moment is the latest live classify act on it, computed at read; the traffic light applies — the record holds the measurement, the class is the band, and the bands re-cut without touching a record. (3) Membership is a VIEW, a fold over classify acts, as a role is a fold over grants. (4) Ceilings read the class: class × action × information class × space, checked when a grant is created and at every act; a reclassified actor loses power at the next act with no grant to hunt.

**On Venn2 the grouping IS the frames** (design/43 §3 carries the first two):

    ORGANISATION frame    nested chains          the structure that CONFERS power; grants attach to nodes
    OCCUPANCY frame       touching instances     the hat, dated; "fire the CEO" = one instance ending
    CLASSIFICATION frame  touching instances     the class, dated; the classify act IS the instance;
                          (actor AD class · info AD class)   ceiling rules attach to class nodes and confer nothing

Relations compose only within one frame (the anti-bleed rule, spec §3): a storage nesting confers nothing organisational and a class confers nothing at all. **The permission view of one actor** is one walk: live occupancy → up the organisation chain collecting grants; live class instances → collecting ceilings; effective power = grants ∩ ceilings (the hardened profile of design/30 §2 with one intersection added).

**Max possible for an actor group — three envelopes, each a view.** CLASS MAX = the intersection of the ceilings on the class node's nested chain: the most any member could ever hold, whatever anyone grants. STRUCTURAL MAX = the union of grants on an org node's nested chain: the most that position can confer at its tip. HELD = the union of the members' effective power now. Held sits inside both at every moment (a test that finds held outside class max is the invariant refusing); class max minus held is unused headroom, the number that says a class is over-provisioned before any act goes wrong.

**One revision, with its reason (2026-09-09).** Earlier in the day the architect said classes stay flat. On Venn2 they may NEST safely, because ceilings compose by intersection and nesting can only tighten; what must stay flat is anything that CONFERS power. Ceilings are the one thing where inheritance runs the safe direction.

## D08.51 — information is governed by tagging the FLOW, not the datum (owner, 2026-09-09: "info isn't static resource even though it is. it is stream of flow. like vehicles types permitted to move between two warehouse… tag of info isnt tag to the static state, but the tag of operatable flow… if we tag all the info flow stream, then the info flowing between them are automatically governed right?")

**Yes, and it is the stronger reading; C5 already built it at the border.** A channel is opened between two established endpoints with a role; a tunnel binds sender, target, permitted class and proof; a socket opens only under a recorded grant of who may reach where; the firewall decides a connection by rule. Each is a tagged flow. **The general law for C6:** information is governed by tagging the opened PATH — a record naming its two endpoints and their classes, the content classes it permits, and the rule it cites; every move of information is an act on a path; ceilings attach to paths, bounded by the two endpoints' classes. The tag says which kinds of vehicle may run this road; the cargo carries only its class.

**Three conditions make "automatically governed" a property rather than a hope.** (1) COMPLETENESS: it holds only if every way information can move is one of the record's path families — today five: channels; sockets and tunnels; shared memory; custody handover; sight (a read is a flow from the record to a reader). The invariant to state and to CENSUS is "no sixth way"; a path nobody tagged is where everything moves. (2) THE DATUM STILL CARRIES ITS CLASS: the path permits classes, so the content must be able to say what class it is (D08.48's leaves; origin — input from the world, output of an AI, a sensor reading — is a computed fact of the record); path first, and the content's class only TIGHTENS. (3) DEPTH INSIDE A PROGRAM: a subprocess-to-subprocess flow inside one master process is inside the two-channel box (design/39); tag flows at the depth a rule can cite, and inside the box stays opaque until a rule opens it — the paper's choice, and where the cost lives.

**The information-side cuts mirror the actor-side cuts, from the object slot.** Processing: structured content may be the input of a structured rule; unstructured content may only be read into a decision by a human or an AI — so a program may hold and move unstructured content, and no grant may make a program the decider over it. Reach: which actor classes may ever be granted sight of a class of information (secret never reaches an external actor; custody content reaches an AI only with a human's countersign). Origin: information the world hands us is INPUT and stays so through every fold; a rule may say "no decision rests on input of this origin alone" — the guaranteed-say rule applied to information. An entity sits in both pictures: an AI is an actor when it acts and information of a class when a rule asks what may be revealed about it.

## D08.52 — does this make the whole thing slimmer? (owner, 2026-09-09: "I guess that would also modularly make things slimmer and more effective right with program and software and ai etc process and what info like etc?")

**Yes, in law; honestly, not in the first build.** The slimming is that every kind of actor (human, AI, program, its processes) and every kind of information (records, content, input from the world, an AI's output) is governed by the SAME FOUR PRIMITIVES — the class vocabulary (one rule), the classify act (one operation), the path families (one shape of record), the ceiling (one shape of rule reading one computed fact) — instead of each subsystem carrying its own permission code. Today the estate already has the per-subsystem instances: files' sight, comms' role contract, sockets' grant, devices' capability, the tunnel's permitted class. Under this law those become five INSTANCES of one path-and-ceiling shape, which is exactly the re-cut the rebuildability rider (design/28 §5, 2026-08-22) reserved: declarations reference kinds by name, so the re-cut is a law pass through the founding door, large but ordinary. What is NOT added: no group object, no member list, no per-datum label, no access-control list, no class that grants, no inheritance of power. What IS added and costs: the completeness census (a new invariant and its instrument), the classify act and its vocabulary (one founding move), and the ceiling check shape (possibly a new check kind — the owner's one word at its gate). Where it lands: the C6 paper, self-orchestrated institutions, whose subject is exactly actors and flows across many bodies; carried there through C6-PAPER-INTAKE §9.

## D08.53 — the core is one record and one gate; a view's "format" is its declaration, not the row's shape (owner, 2026-09-09: "core of gov-os is just a table record with a gate right? that does everything… each view or any derived table should inherit the same format? and handshake between tables?… if view structure is modular, then it is way more customisable right?")

**Yes, with two corrections.** The core: one append-only record of acts, every row one shape (actor, action, object, target, the fields, seq, time, prev_hash, the store's countersignature), and one gate every act crosses, appending the act with its cited rule or a refusal with its cited rule; everything else computed. **Correction one:** three things stand BESIDE the record by law — the bytes (content by hash, design/46), the secrets (the vault, which the record cannot read), the world's inputs (clock, sensor, peer reply — INPUT, never a decision). **Correction two:** a view does not inherit the row's format, because a view is STATE and a row is HISTORY. What every view shares: its DEFINITION is a row (name, the actions that feed it, the rule it answers to; since EP-50 its servicing is a row too); its answer is computed at a seq; its answer has ONE CANONICAL FORM so it can be hashed and compared (design/34 — the fingerprint). That canonical, dated, hashable answer is the "same format".

**Handshake between tables:** none inside one body — views are functions over the one record and may read each other only because they all derive from it; a handshake exists in exactly one place, where a view crosses a body's border, and there it is INPUT to the other body, one row one receipt (C5 N6/N9). A wanted handshake between two views inside one body means one of them holds state it should compute.

**Modular views = a declared vocabulary of DERIVATIONS.** Every check kind is already a small derivation over the record plus a comparison (latest per key; a live set from opens minus closes; a count against a threshold; a field read from a located row). Views are made of the same derivations. Direction: one closed vocabulary of derivations declared in the constitution like the check kinds; a view = a declaration (this derivation, over these actions, keyed thus, answering to this rule); a new view is then a law act through the founding door, not code; the August rebuildability rider applies to views and checks together because they are one thing seen from two sides. CAP: today the derivation bodies are code (design/28 §10, the S-plane); the declarations are rows. PLACEMENT: after C6 (institutions), when many bodies each want views over shared shapes — a campaign-sized law pass.

## D08.54 — the brake: a deciding-time problem, answered by a FROZEN, NEGATIVE-ONLY view, no second kernel (owner, 2026-09-09: "that is a problem of deciding time, not recording time right? does that need a new mini-govos to just do brake, or an effective view can already do the compliance role?… we can basically freeze the view so it doesnt do rule changes, only 'compliance work'?")

**Yes.** The record already separates deciding time from recording time: an actor acts against a computed view of its power, the local view refuses before the act travels, the gate confirms at the record (design/30 §2). A brake is a refusal with a deadline; the deadline is the only new thing.

**The brake view has three properties, each already a law:** (1) FROZEN — computed as of one seq and sealed with its fingerprint; it does not move while it serves (a stale view is what the fingerprint check refuses, so a frozen view is a known object). (2) NEGATIVE-ONLY — it may stop, refuse, hold, drop; never permit beyond what the record permitted at the freeze, never grant, never change a rule ("compliance work only"). (3) ACTS BEFORE ITS ROW LANDS — D08.52's principle in its safe direction: a stop leaves the world no worse if unrecorded, so a stop may precede its record; a permit may not; the stop is appended LATE as a row citing the frozen view's seq and fingerprint, so the record always says under which law the brake fired.

**Staleness has a safe and an unsafe direction.** A rule LOOSENED after the freeze is not yet honoured — the brake over-stops (fail-closed). A rule TIGHTENED after the freeze would be missed — so the freeze is RE-CUT on every change to the view's fold set (EP-50's mandated-view servicing is the mechanism), and while a tightening is appended but the re-freeze has not landed the brake treats the world as under a pending tightening and STOPS. Changing rules fast cannot soften the brake; it can only make it stop more.

**When it lives in a second body:** if the deadline is shorter than the round trip to the record (a device controller, the guest), the frozen view SHIPS to that body as a RENDERING with its fingerprint (the C4 rendering law), and the gate runs there in negative-only mode — holds the frozen prefix, appends nothing but its own stops, reconciles back by one row one receipt. That is the "mini gov-os": the same gate, a frozen prefix, a rule that permits are not served here. The guest already has the shape.

**What must be MEASURED, never designed:** the time from a tightening's append to the brake's re-freeze, on the hardware in question — the brake's honest deadline, C7's timing spike (D08.26/27). Until taken, the claim is "stops under law as of its last freeze", never "stops within X". PLACEMENT: C7 (self-hosting) — the first view served to another body with a deadline; C6 gives it the class ceilings first (an AI never holds the actuator reach).

## D08.56 — the deriving audit of D08.49–D08.55 at the architect's hand (owner, 2026-09-09: "also a modular, definitive etc check on the actor, info and view thinking we wrote")

Method: each claim re-read against the minimality gate (is it unbreakdownable, or derivable from what the record already has?) and the definitive test (does it sit at the root, or at a surface?). Six findings, each a SIMPLIFICATION or an AXIS CLARIFICATION; none reverses a ruling; three reduce what C6 must mint. Costs stated.

**F1 — the actor classes are BANDS on the processing cut, not a species list (D08.49).** Human / AI / program are display names for two capabilities: may-be-the-arm-of-a-structured-rule and may-be-the-arm-of-an-unstructured-rule — human (both), AI (u only), program (s only). The definitive is the capability pair; the names are the traffic light's colours. SO: the vocabulary rule declares the two capabilities; a class name is a label over a pair; a new species (a hybrid, a sensor with judgment) is a new pair, not a new law. CUTS a founding move to two booleans. Cost if wrong: a fourth capability appears that the pair cannot express — then the pair grows by one declared bit, still no species list.

**F2 — "system" and "external" are not actor classes; they are positions on a SECOND AXIS (D08.49's open question, answered by derivation).** design/43 §5 already names the boundary classes — glassboxed (inside the box), the border entity (IS the box's edge), external (outside, channel-bounded). That is a different axis from processing: an AI is glassboxed AND u-only; a peer body is external AND unknown-processing. So there are THREE AXES, not one class list: PROCESSING (D08.49's cut), BOUNDARY (design/43 §5), REACH (which path families and counterpart positions an actor may open — D08.49's second cut). On Venn2 each axis is its own frame of touching instances; ceilings read any axis; nothing composes across frames (the anti-bleed rule already ruled). The owner's word is still his; the derivation says "external" is a boundary position and needs no fourth processing class. Cost if wrong: none — a wrongly placed value moves frames, not law.

**F3 — "classify" is not a new act; it is ATTEST generalised (D08.50).** VERIFY-ACCOUNT already IS "record a fact about an actor with an evidence hash and a verifier". A classify act (object = entity or information, target = the band, evidence, rule) is the same shape with a target; the D08.48 identity leaves are the same shape again (a fact, salted, revealable). SO: one act family ATTEST — verify-account, classify, leaf — three instances; membership, class and leaves are three folds over one act kind. CUTS a new operation from C6's founding move to an amendment of one existing op's params (the op-amend lesson: the META declares the new field). Cost if wrong: a fact whose evidence form is not a hash — then ATTEST gains an evidence kind, still one act.

**F4 — the ceiling needs NO NEW CHECK KIND, likely (D08.50's "possibly one check kind").** A ceiling asks: locate the ACTING entity's latest attest-of-band, read its band, compare to the allowed set. That is `prior_value` (locate the latest row by action + field + key, read a field out of THAT row) composed with `value_domain` (the value is in a declared set) — both exist. The one gap: prior_value locates by a PARAM; the ceiling must locate by the ACTOR, the engine's fact. `live_present` already admits `$actor` as a key source (EP-49C). SO: `prior_value` gains `$actor` as a locate source — a well-formedness door change to an existing kind, not a new kind; the owner's gate for a new word is not reached. Marked LIKELY: confirmed only by the paper driving a real ceiling row through the door. Cost if wrong: one new kind and one owner word — the state D08.52 already priced.

**F5 — the "path" is a VIEW over the five families, not a new record (D08.51).** Channels, sockets/tunnels, shared memory, custody, sight each already have their open act, endpoints and permitted class in the record. A PATH is the fold that reads the five into one shape (family, endpoints, their positions on the three axes, permitted content bands, cited rule); ceilings attach to that shape; the "no sixth way" invariant is an INSTRUMENT over the code (the effect-order census's sibling: every place bytes move is one of five families) — not a rule the record can check about itself. CUTS a founding move; ADDS one census. Cost if wrong: a family whose open act carries too little to fold — then that family's op gains a param (an amendment), never a PATH op.

**F6 — origin is already a field (D08.51).** C5's crossing law tags every row INPUT or DECISION (record_class). "Information the world hands us stays INPUT through every fold" is that field read, not a new one; the origin ceiling ("no decision rests on input of this origin alone") is a rule over rows carrying INPUT and their source position. Nothing to mint.

**Consistency across the seven (preserve, don't smooth):** D08.50's "flat" and its same-day revision "may nest" stand as written with the reason (ceilings compose by intersection). D08.54's brake acting before its row lands does not contradict D08.53's gate-appends-every-act: the stop is appended late, citing the frozen view — and it is the D08.52 principle in its safe direction, not an exception to it. D08.53's "one handshake, at the border" and D08.54's second body reconciling by receipt are the same border. No CONFLICT stands.

**What the audit changes in C6's price:** founding moves drop from three (class vocabulary, classify op, path op) to ONE amendment plus two declarations (ATTEST gains a target and evidence kind; the vocabulary declares two capabilities and the boundary positions); the check kind probably stays at nineteen; one new instrument (the five-families census). What it does not change: the ceilings still only shrink; the grant is still the one source of power; nothing stores a status.
